What this is

A browser-driven load-testing tool for Power BI / Fabric capacities. Embeds a Power BI report via the JavaScript SDK and cycles through filter, slicer, bookmark, and page combinations to simulate real users — defeating query cache for realistic uncached renders.

Each refresh's wall-clock duration, applied state, and metadata is captured to .jsonl log files for offline analysis. Run multiple browser instances simultaneously to simulate concurrent users.

What's new in v1.0 Stage 1

  • Playwright runner replaces CefSharp. A small Node script (runner/run.js) launches N Chromium contexts at http://localhost, captures console.log('METRIC ...') from each, and writes JSONL to disk. Fixes multi-window MSAL.
  • Run with node run.js --concurrency N instead of Run_Load_Test_Only.ps1.
  • Deleted: ChromeWriteBack/, Run_Load_Test_Only.ps1, Update_Token_Only.ps1, PBIToken.json template, and the CefSharp.PostMessage writeback path in the HTML. Single auth path (MSAL), single writeback channel (console).

Carried forward from v0.8.0

  • Vendored powerbi-client 2.23.1 — replaces dead cdn.rawgit.com.
  • MSAL.js silent token refresh.
  • JSONL log output.
  • Off-by-one fix — runs stop exactly at numberOfViews.
  • jQuery removed.
  • In-page Setup picker for ad-hoc runs.

Prerequisites

For the in-page picker / single-window manual use:

  • A modern browser (Chrome / Edge / Firefox).

For multi-instance via the Playwright runner (Stage 1):

# One-time machine setup
cd RealisticLoadTestTool/runner
npm install
npx playwright install chromium    # ~150MB browser binary

For the legacy Setup_Load_Test.ps1 scenario generator (still works in Stage 1):

# Run in elevated PowerShell (one-time)
Set-ExecutionPolicy Unrestricted
Install-Module -Name MicrosoftPowerBIMgmt

One-time: configure MSAL (mandatory)

MSAL is the only auth path. Configure once, then no manual token refreshes ever.

  1. Tenant admin: register a Single-Page Application in Entra ID (full instructions in _Documentation/MSAL-app-registration.md). Note the Application (client) ID and Directory (tenant) ID.
  2. In RealisticLoadTestTool/, copy auth-config.example.json to auth-config.json.
  3. Paste your client ID and tenant ID into auth-config.json. (This file is gitignored.)
  4. Either run the Playwright runner (recommended — see Workflow below) or serve HTML manually: 
    python -m http.server 8080
# Browser: http://localhost:8080/RealisticLoadTest.html
  5. Sign in once. The page silently refreshes the token forever after.
Multi-window MSAL works in Stage 1. The runner serves HTML over http://localhost and uses one persistent Chromium profile, so all windows share the same MSAL cache — sign in once in the first window and every subsequent window acquires silently.

Workflow

  1. (Optional) Configure a scenario via Setup_Load_Test.ps1 — prompts for workspace, report, views, think time, project name and writes a populated PBIReport.json into a per-test subfolder. (Or skip this and edit the root PBIReport.json directly. Stage 1 only invokes the root config — subfolders are scenario archives until Stage 4.)
  2. Launch the load test: 
    cd RealisticLoadTestTool/runner
node run.js --concurrency 4
    Opens 4 Chromium windows, all serving the configured scenario from http://127.0.0.1:8765/RealisticLoadTest.html.
  3. First run only: click "Sign in with Microsoft" in the first window. The MSAL token caches in the run's browser profile and all subsequent windows acquire silently.
  4. Watch the metrics panel and the JSONL flow into Test Results/<run>/<instanceId>.jsonl.
  5. The runner exits cleanly when every instance has emitted view_limit_reached. Or Ctrl+C to stop early — partial JSONL is still valid.

Single-window manual use (no Playwright dependency):

cd RealisticLoadTestTool
python -m http.server 8080
# Browser: http://localhost:8080/RealisticLoadTest.html

Output: JSONL schema

Each refresh writes one JSON object per line. Full schema in _Documentation/JSONL-schema.md.

{
  "ts": "2026-05-03T14:23:01.421Z",
  "event": "rendered",
  "instanceId": 5992180,
  "runId": "2026-05-03T14-22-15-r3a7e",
  "projectName": "capacity-stress-q2",
  "workspaceId": "7bbb6481-...",
  "reportId": "ce7dc7f9-...",
  "pageName": "ReportSection...",
  "bookmark": "Bookmark...",
  "filters": [],
  "slicers": [...],
  "view": { "current": 3, "target": 15 },
  "durationMs": 6101,
  "isFirstRender": false,
  "thinkTimeSec": 1
}

Quick parsing examples:

# Steady-state durations only (excluding cold-start renders)
jq 'select(.event=="rendered" and .isFirstRender==false) | .durationMs' *.jsonl

# Errors
jq 'select(.event=="error")' *.jsonl

# p95 by bookmark (steady-state)
jq -s '[.[] | select(.event=="rendered" and .isFirstRender==false)] | group_by(.bookmark) | map({ bookmark: .[0].bookmark, p95: (sort_by(.durationMs) | .[length*0.95 | floor].durationMs) })' *.jsonl

PBIReport.json reference

{
  "reportUrl": "https://app.powerbi.com/reportEmbed?reportId=...&groupId=...",
  "pageName": "ReportSection123",
  "bookmarkList": ["Bookmark1a2b3c","Bookmark4d5e6f"],
  "filters": [
    {
      "filterTable": "SalesData",
      "filterColumn": "Region",
      "isSlicer": true,
      "filtersList": ["North","South","East","West"]
    }
  ],
  "thinkTimeSeconds": 5,
  "numberOfViews": 50,
  "sessionRestart": 100,
  "projectName": "capacity-stress-q2",
  "layoutType": "Master"
}
FieldNotes
numberOfViewsHard stop after this many refreshes per instance. v0.8 is off-by-one fixed.
sessionRestartEvery N refreshes, the tab reloads to mitigate iframe memory leaks. 100 is sane.
layoutTypeMaster / MobilePortrait / MobileLandscape
filters[].isSlicertrue → applied as slicer state; false → as report-level filter
filters[].filtersListEach item: single value, array (multi-select), or null at start (= "all non-null in this list")
pageNameInternal ReportSection<id> — find it in URL when the page is active in app.powerbi.com
bookmarkList[]Internal bookmark names — find via URL
projectNameFree-text tag, propagates into every JSONL row for traceability

Troubleshooting

IssueSolution
Page is blank, no metricsOpen DevTools → Console. Look for MSAL initialization failed or token errors. Verify auth-config.json values + that the page's origin is registered in the Entra SPA app's redirect URIs.
Runner: Playwright is not installedRun npm install in RealisticLoadTestTool/runner.
Runner: Executable doesn't existRun npx playwright install chromium from RealisticLoadTestTool/runner.
Runner: all instances emit auth_failure in headless modeThe shared MSAL cache is empty or expired. Run once headed first to populate it.
AADSTS50011 redirect URI mismatchThe URL the page is served from isn't in the SPA app's redirect URI list. Add it (Entra → App registration → Authentication). Note: Entra matches the full origin including port — http://localhost ≠ http://localhost:8080.
popup_window_error: Error opening popup windowShould not occur in v0.8.0+ — fixed in T5a by adding an explicit "Sign in with Microsoft" button (popups now fire from a user click, which browsers always allow). If you see this error, you're on a pre-T5a build; either upgrade or click the blocked-popup icon in the address bar to allow pop-ups for http://localhost:8080 and reload.
AADSTS65001 consent requiredApp registration permissions not granted at admin level. Re-grant admin consent.
JSONL is truncated mid-lineThe browser was killed mid-write. Discard the partial line; jq will show the parse error.
High client CPU usageReduce instances per host. Rule of thumb: 1 browser per physical core. v1.0 adds a host resource monitor that flags this automatically.

Best practices

  • Set think time to 5–10 s while validating; reduce to 0–1 s for actual load tests.
  • 1 browser instance per physical CPU core. More than that and you're measuring browser limits, not Power BI limits.
  • sessionRestart between 100–200.
  • Always pair the front-end results with the Fabric Capacity Metrics App for back-end CU consumption — front-end render time alone doesn't capture the smoothing/throttling story.
  • Don't run tests during business hours on shared/production capacities.
  • Even enterprise BI rarely has >10 truly simultaneous queries — most realistic load tests are 5–15 concurrent with 15–60 s think time, not 50 hammering browsers.
