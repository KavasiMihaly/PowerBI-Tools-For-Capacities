## Summary

The Node-based resource monitor (`RealisticLoadTestTool/resource-monitor/monitor.js`) samples host CPU + RAM at 1 Hz, posts each sample to the coordinator's `POST /host-metrics` endpoint, and writes a local audit JSONL. A 30-second rolling-window saturation flag debounces transient spikes and latches `hostSaturated` true/false. The dashboard reflects it in real time; `RealisticLoadTest.html` polls `/status` every 5 s and stamps `host_saturated: true` on any metric record emitted while the flag is on.

All three Stage 3 tests pass. Implementation differs from the original plan in two ways (both already documented in `resource-monitor/README.md`): Node + built-in `os` module replaces Python + psutil, and CPU + RAM only — no per-core, network I/O, or GPU (deferred to Stage 4+).

## TEST-V10-06 — In-browser flag propagation

Active load test running concurrently with burner (`numberOfViews: 30`, `thinkTimeSeconds: 3`, single browser instance via `RealisticLoadTest.html` opened directly — no Playwright runner this run).

**Burn-window timing:**

| Event | Timestamp (UTC) |
|---|---|
| Burner start | 16:48:08.742Z |
| Monitor flag latches `saturated: true` | 16:48:41.135Z (first record) |
| Burner stop | 16:48:55.589Z |
| Monitor flag clears | 16:49:24.485Z (last `saturated: true`) |

**Render-duration progression around the burn** (extracted from coordinator metrics buffer at `Test Results/stage3-validation-20260521/coordinator-metrics-buffer.jsonl`):

| View | Emit time (UTC) | `durationMs` | `host_saturated` |
|---|---|---|---|
| 27/30 | 16:47:59.287Z | 5,130 | absent (pre-burn) |
| 28/30 | 16:48:08.111Z | 5,824 | absent (burn just started, flag not latched) |
| 29/30 | 16:48:18.863Z | 7,752 | absent (10 s into burn, flag not latched) |
| **30/30** | **16:48:55.269Z** | **33,406** | **`true`** ✓ |
| `view_limit_reached` | 16:48:58.780Z | — | **`true`** ✓ |

The 5.1 s → 7.8 s → 33.4 s render-time progression is exactly the "invalid data" pattern the saturation flag is meant to make filterable — the host CPU was pinned for the duration of the last render, ballooning its wall-clock by ~7x.

**Pass criteria check:**
- ✅ Records emitted while the monitor flag is true carry `host_saturated: true` (2 records).
- ✅ Records emitted before the latch do not carry the field (omission = not saturated; 31 records).
- ✅ Both stamped records fall inside the monitor's saturation window (16:48:41–16:49:24).

**Note on alignment:** The browser polls `/status` every 5 s, so the stamp tracks the page's last-polled flag state at emit time, not the monitor's instantaneous state. In normal operation the gap is ≤ 5 s. During heavy saturation, individual renders can stretch to 30+ s; in that case the flag stamping correctly reflects the state at record emission rather than at render start. The test plan's "±10 s" alignment tolerance is appropriate for steady-state renders; for renders that span the latch transition, the emit-time semantics are what matters.

## Findings outside Stage 3 scope

These came up while running the tests. None block Stage 3, but worth backlog rows:

1. **Cold-start render p50 is ~60 s.** First-time MSAL popup + SDK init + first iframe load combined. Already understood (the `isFirstRender: true` flag was added in v0.8 specifically to let analysis split warmup from steady state), but worth flagging that for short test runs (< 10 views) the cold-start dominates the average. No action needed unless a future test plan wants a "warmup window" mechanism.
2. **Embedded iframe vertical size feels cramped.** The outer `#embedDiv` has `min-height: 800px` and the embed uses `LayoutType.Master`, but in the operator's browser viewport the report canvas was visually constrained — they reported "the iframe is really narrow" / "it is just pretty small". The renders completed correctly and metrics flowed normally, so this is a UX polish issue, not a correctness issue. Candidate backlog row for a v1.0.x patch or to fold into Stage 5's Setup wizard work: review `LayoutType` choice and consider `Custom` with explicit width/height that fill the container, or remove the master-page letterboxing.
3. **Stale `auth_failure` instance lingers in `/status.instances`.** A prior browser attempt (instanceId 6162320) with `view 0/10` shows `active: false` but is still in the array. The coordinator should age-out inactive instances after some interval, or `/status` should filter them. Minor — doesn't affect aggregation since only active instances contribute.
