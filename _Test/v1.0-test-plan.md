# RealisticLoadTest v1.0 — Test Plan

**Source plan:** `_Plan/realisticloadtest-v2.md` (§Phase v1.0 + §Test plans)

## Pre-requisites for running any test

1. v0.8 fully shipped and tested.
2. v1.0 build deployed to a fresh test folder.
3. Demo `.pbix` deployed to a Power BI workspace.
4. Entra app registration completed (carried over from v0.8).
5. Node.js installed on the test machine (for the coordinator).
6. Python 3 + `psutil` installed (for the resource monitor).
7. For TEST-V10-10 / TEST-V10-11: a fresh Windows VM that has nothing installed beyond Chrome.

## Tests

### TEST-V10-01: End-to-end browser-only setup flow

**Verifies:** B2 / T8 — replacing PowerShell setup with a web UI.

**Prerequisites:** v1.0 build.

**Steps:**
1. Open `RealisticLoadTestTool/Setup.html` in Chrome.
2. Sign in via MSAL popup.
3. Pick a workspace from the dropdown (populated via `GET /groups`).
4. Pick the demo report from the report dropdown (populated via `GET /groups/{id}/reports`).
5. Pick a page from the page dropdown (populated via `GET /reports/{id}/pages`).
6. Pick one or more bookmarks (populated via `GET /reports/{id}/bookmarks`).
7. Define a filter using the column picker (populated via dataset metadata).
8. Set concurrency=2, viewsPerSession=10, thinkTimeSec=5, project name="ui-smoke-test".
9. Click "Generate config".
10. A `loadtest.yaml` appears at the path the user selected.
11. Click "Run".
12. Two browser windows open. Both render the report.

**Pass criteria:**
- All dropdowns populate with real data from REST APIs.
- `loadtest.yaml` parses and matches schema.
- Two windows open and start producing JSONL.
- No PowerShell prompts opened during the entire flow.

**Fail criteria:**
- Any dropdown is empty or shows an error.
- Generated YAML fails to validate.
- `Run` opens the wrong number of windows or fails silently.

### TEST-V10-02: `loadtest.yaml` schema validation

**Verifies:** T9.

**Prerequisites:** v1.0 build, `loadtest.example.yaml`, schema document at `_Documentation/loadtest-yaml-schema.md`.

**Steps:**
1. Validate `loadtest.example.yaml` against the documented schema.
2. Mutate the YAML in 3 ways (missing `workspace`, malformed `filters`, negative `concurrency`).
3. Each mutation should produce a clear error message at config-load time.

**Pass criteria:**
- Example YAML validates clean.
- Each mutation is rejected with an actionable error message naming the offending field.

**Fail criteria:**
- Any mutation accepted silently.
- Example YAML produces a warning.

### TEST-V10-03: YAML migration from v0.8 per-folder JSON

**Verifies:** T9 — backwards compat for users with existing v0.8 setups.

**Prerequisites:** A v0.8 test folder with the per-folder `PBIReport.json`, `Filters.json`, `Bookmarks.json`, `Page.json`.

**Steps:**
1. Run `migrate-config.ps1 <v0.8-folder>` (or `node coordinator/migrate.js <v0.8-folder>`).
2. Inspect the resulting `loadtest.yaml`.
3. Run the migrated config against the same demo `.pbix`.
4. Compare metrics to a fresh v0.8 run on the same scenario.

**Pass criteria:**
- Migration produces a valid `loadtest.yaml`.
- Metrics from the migrated run match the original scenario within ±5%.

**Fail criteria:**
- Migration loses any filter, bookmark, or page-name detail.
- Migrated run produces a different scenario than the original.

### TEST-V10-04: Resource monitor sampling at 1 Hz

**Verifies:** B3 / T10.

**Prerequisites:** v1.0 build, monitor running.

**Steps:**
1. Start the resource monitor: `python tools/resource-monitor/monitor.py --out Test\ Results/test/`
2. Wait 60 seconds.
3. `wc -l Test\ Results/test/host-metrics.jsonl`
4. `head -1 Test\ Results/test/host-metrics.jsonl | jq 'keys'`

**Pass criteria:**
- Step 3 returns ~60 lines (±2 for startup/shutdown).
- Step 4 includes: `ts`, `cpu_percent`, `cpu_per_core`, `mem_percent`, `mem_used_mb`, `net_sent_bytes_sec`, `net_recv_bytes_sec`.

**Fail criteria:**
- Sampling rate noticeably different from 1Hz.
- Missing any of the documented fields.

### TEST-V10-05: Resource monitor saturation flagging

**Verifies:** B3 / T10 — the saturation banner per user decision (log + warn + flag, no auto-pause).

**Prerequisites:** v1.0 build, monitor + dashboard running.

**Steps:**
1. Start a load test.
2. Open a separate terminal.
3. Run a CPU-burner: `for i in 1 2 3 4; do yes > /dev/null & done` (or `stress-ng --cpu 8 --timeout 60s` if available).
4. Wait 35 seconds.
5. Observe dashboard banner.
6. `cat Test\ Results/<run>/host-metrics.jsonl | jq 'select(.host_saturated==true)' | head -1`
7. Kill the burners.
8. Wait 35 seconds.

**Pass criteria:**
- Step 5: dashboard shows saturation banner within 30–35s of CPU burners starting.
- Step 6: at least one record with `host_saturated: true`.
- Step 8: banner clears within 30s of killing burners.

**Fail criteria:**
- Banner doesn't appear.
- `host_saturated` field missing from output.
- New browser instances spawn during saturation (auto-pause was explicitly NOT requested — verify this DOESN'T happen).

---

### TEST-V10-06: Saturation flag propagates to in-test metric records

**Verifies:** B3 / T10 — the in-browser metric records during saturation are tagged so analysis can filter them out.

**Prerequisites:** Same as TEST-V10-05.

**Steps:**
1. Repeat saturation steps from TEST-V10-05.
2. `cat Test\ Results/<run>/<instanceId>.jsonl | jq 'select(.host_saturated==true) | .ts' | head -3`
3. Compare timestamps to host-metrics.jsonl saturation window.
4. `cat Test\ Results/<run>/<instanceId>.jsonl | jq 'select(.host_saturated==false) | .ts' | head -3`

**Pass criteria:**
- Step 2: test-metric rows captured during saturation window have `host_saturated: true`.
- Step 4: test-metric rows outside the saturation window have `host_saturated: false` (or omitted).
- Timestamp alignment is within ±2s of host-metrics.jsonl.

**Fail criteria:**
- Saturation window timestamps don't align between the two files.
- All rows or no rows have the flag (binary failure).

### TEST-V10-07: Live dashboard renders p50/p95 within 2s of new data

**Verifies:** T11.

**Prerequisites:** v1.0 build, coordinator running, demo .pbix configured.

**Steps:**
1. Start a load test with concurrency=3, viewsPerSession=20.
2. Open `http://127.0.0.1:7878/dashboard` in a separate Chrome window.
3. Watch the metrics counters update.
4. Inspect the page source — confirm a polling/EventSource mechanism updates every ≤2s.
5. Use DevTools → Network → fetch/EventSource view to confirm.

**Pass criteria:**
- Total refresh count increments at the rate it's actually happening (visible new rows in JSONL within 2s of dashboard tick).
- p50 and p95 render durations are computed and shown.
- Per-report breakdown shown.
- Concurrent instance count = 3.
- Error events (if any) shown.

**Fail criteria:**
- Dashboard data is stale by >5s.
- p50/p95 missing or showing NaN.
- Instance count is wrong.

### TEST-V10-08: Coordinator HTTP API — `POST /metric` accepts JSONL line

**Verifies:** T11 / B4b — the architectural API for v2.0 multi-VM scale-out.

**Prerequisites:** v1.0 build, coordinator running on `127.0.0.1:7878`.

**Steps:**
1. Construct a synthetic JSONL line in the documented schema.
2. `curl -X POST http://127.0.0.1:7878/metric -H "Content-Type: application/x-ndjson" -d '<jsonl-line>'`
3. Inspect the response.
4. Verify the line appears in the dashboard.

**Pass criteria:**
- Step 3: response 200 with `{"accepted": 1}` body.
- Step 4: the synthetic refresh count appears in the dashboard total.

**Fail criteria:**
- Non-2xx response.
- Line silently dropped without error.

### TEST-V10-09: Coordinator security — localhost-only by default

**Verifies:** T11 — security default per plan §Security considerations.

**Prerequisites:** v1.0 build, coordinator running on default settings (no `--bind 0.0.0.0` flag).

**Steps:**
1. Get the machine's LAN IP: `ipconfig` (Windows) or `ip addr | grep inet`.
2. From a second machine on the same LAN: `curl http://<lan-ip>:7878/dashboard`.
3. From the same machine: `curl http://localhost:7878/dashboard`.

**Pass criteria:**
- Step 2: Connection refused / timeout — coordinator does not accept LAN traffic by default.
- Step 3: HTML returned successfully.

**Fail criteria:**
- Step 2: HTML returned — security regression, coordinator is exposing dashboard to LAN.

### TEST-V10-12: Architecture readiness — remote `POST /metric` works in dev mode

**Verifies:** B4b — the multi-VM architecture is actually ready, not just designed.

**Prerequisites:** v1.0 build, coordinator started with `--bind 0.0.0.0 --dev` flag (development mode that disables the localhost-only check).

**Steps:**
1. From a second machine on the same LAN: `curl -X POST http://<lan-ip>:7878/metric -H "Content-Type: application/x-ndjson" -d '<synthetic-jsonl-line>'`.
2. Inspect dashboard on the host machine.

**Pass criteria:**
- Step 1: response 200.
- Step 2: the synthetic refresh count appears in dashboard.
- Console output on host shows the source IP that submitted the metric (audit trail).

**Fail criteria:**
- Connection refused.
- Metric is silently rejected without error.

**Note:** This is an architecture-readiness check, not a security claim. v2.0 will add proper auth on this path before it's production-usable. Document this clearly in `_Documentation/v2-distributed-architecture.md`.
